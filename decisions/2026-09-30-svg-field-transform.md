# SVG field-space transform and snap-toggle default

Status: accepted implementation decision for Kanban tasks `t_5f14225f` and `t_57b25e2c`.

DECISION | J | Default graphical football-field orientation | Present canonical y=0 (front sideline) at the bottom of the rendered field and canonical y=widthUnits (back sideline) at the top, without changing canonical coordinates or horizontal side ordering. | J explicitly corrected the prior graphical orientation. | `createFieldTransform` and its inverse flip only the SVG presentation y axis; stored dots, field geometry, coordinate formatter, setup-wizard layout, motion logic, schema, and fixtures remain unchanged. SVG boundary extents and label rows must be normalized so the flip cannot create a negative rectangle or inverted text.

DECISION | Wheeljack | Correct SVG field click interaction | A click on a valid field location moves the currently selected performer's existing dot using `store.apply({ type: 'dot.move', ... })`; it uses the same snap-toggle behavior, bounds validation, and undo/redo history as drag-to-move. It does not create a dot. | The real command store enforces complete set coverage: every active performer has exactly one dot in every existing set. A performer-without-a-dot click target is therefore not reachable in the production document model, and the prior fake-store click-to-create test bypassed the invariant rather than exercising a real application state. | This supersedes only the click-to-place/click-to-create portion of the following implementation record. The coverage invariant and command-store validation remain unchanged; the SVG editor has no `dot.create` click path.

DECISION | Wheeljack | SVG field rendering transform and default drag-snap behavior | Render the NFHS 11-player field in a fixed 980x560 SVG viewBox (900x480 playing-field box plus a 40px margin) built from a pure, stateless `createFieldTransform(field)` (`src/editor/field-geometry.ts`) that maps canonical field units (FU) to SVG pixels and back. The field box's 900:480 pixel ratio exactly matches the field's 288000:153600 = 15:8 FU ratio, and 480 is divisible by 3, so the 50-yard line and both hash marks (at exact 1/2 and 1/3, 2/3 fractions of their axis) land on exact integer pixel coordinates rather than rounded approximations. Drag-to-move and click-to-place default to snapping the pointer's field-unit position through the existing, independently verified `snapToQuarterStepGrid` (`src/geometry/coordinate-builder.ts`) — reused directly, not reimplemented — with a visible checkbox (not buried in a menu) to disable snapping for free integer-FU placement. Every placement/move still dispatches through `store.apply` with the same `dot.create`/`dot.move` commands, `isValidDot` bounds checking, and undo/redo history as the structured form; SVG pixel coordinates are computed on every render from the canonical document state and are never written into `FreeformDocument` or the command history. | The M1 decision record (`decisions/2026-09-29-m1-app-shell-stack.md`) requires canonical FU to remain sole source of truth and forbids persisting SVG pixels; a pure, reconstructible transform function (rather than a stored transform/state object) makes that structurally impossible to violate. An exact-integer-pixel landmark mapping lets acceptance tests assert exact rendered positions instead of tolerance-based approximations, directly satisfying this card's acceptance criterion 1. Reusing `snapToQuarterStepGrid` instead of reimplementing snapping avoids introducing a second rounding convention, per that function's own design intent (`decisions/2026-09-30-derived-coordinate-input.md`). Snap-on-by-default matches J's stated requirement (quarter-step snapping by default, toggle to disable) and matches the structured form's existing quarter-step-first philosophy. | Open questions/consequences: the fixed 980x560 viewBox scales via the SVG's own `width`/`height`/`viewBox` (standard SVG responsive behavior) rather than a dynamic per-container recomputation; this is presentation-only and does not affect stored coordinates. Full keyboard-operable drag-equivalent placement on the SVG surface is explicitly deferred (see the accessibility note in the associated handoff) to M10 per spec §8; the existing structured form and inspection table remain the fully keyboard/screen-reader-operable path today, satisfying spec §6's accessible-equivalent requirement without regression. The SVG editor's toolbar (set/performer selectors) duplicates selection already available in the structured form; this is intentional so the graphical surface is usable standalone, not a replacement for the form.
