# M7.2 IndexedDB autosave, history, recovery, and backup services

Status: accepted implementation decisions for Kanban task `t_aa17f77c`.

DECISION | Wheeljack | Working-copy write ordering | Every working-copy write carries the command store's monotonically increasing `revision` as the IDB record's ordering key; a write is applied only if its revision is strictly greater than whatever is currently stored for that document ID, inside the same read-modify-write transaction. | A slow autosave flush, a late explicit-save completion, and a document switch can all race to write the same document ID; only a revision-gated compare-and-write inside one transaction can guarantee the newest edit always wins regardless of completion order. | A rejected stale write reports `stale-revision` rather than throwing, so callers that don't care about the outcome (e.g. a background autosave) can ignore it safely, while a caller that does care (e.g. explicit save) can detect and react.

DECISION | Wheeljack | Autosave scheduling is pure and timer-injectable | `createAutosaveScheduler` takes only `setTimeout`/`clearTimeout` and an `onFlush` callback; it has no IndexedDB or document knowledge. The idle timer (2s) resets on every edit; the deadline timer (30s) is armed once per burst and never pushed out, bounding worst-case staleness. | Exact boundary behavior (1999ms vs 2000ms, deadline firing despite continuous edits) is only reliably testable with fake timers, and coupling the timing policy to IDB would make every timing test also an async IDB test. | A caller must supply its own flush (typically a working-copy write); the scheduler itself makes no durability claim and never retries a failed flush on its own.

DECISION | Wheeljack | Command-store subscription without modifying the reviewed M7.1 store | `observeCommandStore` wraps a `CommandStore` and emits `apply`/`undo`/`redo` events only for calls that actually changed state (an `apply` that throws is caught by the caller invoking it, the wrapper's `apply` return never completes, and no event fires). | The M7.1 command store is already independently reviewed and must stay byte-identical; a decorator preserves "failed commands produce no snapshot" for free because `store.apply` throws before returning and the wrapper's notification line is simply never reached. | Any M7.3 UI wiring must call the bridge's returned store, not the raw one, or autosave/history will silently stop observing edits.

DECISION | Wheeljack | Version-history retention is "both" not "either" | A checkpoint survives pruning only if it is BOTH among the latest 50 for its document AND created within the last 30 days; the spec's "latest 50 OR 30 days, whichever removes first" is implemented as an intersection (`age <= 30d` filter, then keep newest 50 of what remains). | "Whichever removes first" means each rule is independently sufficient to delete a checkpoint, so a checkpoint must pass both tests to be retained — the two limits compose as AND on survival, not OR. | A document with very frequent explicit saves can still lose a checkpoint younger than 30 days if 50 newer ones exist; this is the intended, spec-consistent behavior, not a bug.

DECISION | Wheeljack | Destructive-operation hook never runs the operation on checkpoint failure | `runWithDestructiveCheckpoint` calls `operation()` only after `versionHistory.recordCheckpoint(...)` resolves; a rejected checkpoint returns `{ ok: false, reason: 'checkpoint-failed' }` and `operation` is never invoked. | A safety net that can silently fail open (run the destructive change anyway when the backup didn't actually get written) is worse than no safety net, because it looks safe. | Every M7.3 bulk-delete/replace UI path must route through this hook and treat `ok: false` as "the operation did not happen," surfacing the message rather than retrying silently.

DECISION | Wheeljack | File-ancestry baseline treats a successful download fallback as equivalent to a direct write | `AncestryStore` records `source: 'download' | 'file-system-access' | 'import'` with a timestamp; the recovery service's "newer than ancestry" comparison is a strict `>` against whichever baseline exists, regardless of which of the three sources produced it. | The user holds current bytes immediately after a successful browser download exactly as much as after a direct permissioned write — the app's lack of a writable handle for next time is a save-adapter concern (already decided in M7.1), not a basis for treating the content as unsaved. | A startup recovery candidate list must not flag a document as "newer than its file" solely because the last save happened to go through the download fallback instead of File System Access.

DECISION | Wheeljack | Recovery candidates never load without validating stored bytes first | `loadCandidate`/`confirmReplace` always re-run `decodeDocument` on the stored working-copy JSON before returning it as `{ ok: true, document }`; a corrupted record, or one that is schema-invalid (including a stored future-major record), returns `{ ok: false, reason: 'invalid' }` instead. | Storage-layer corruption (partial write, unexpected shape) must never be handed to the command store as if it were a valid document; "validate before any imported/recovered write" from spec §6 applies identically to a recovered IndexedDB record as to an opened file. | `discardCandidate` remains available even when `loadCandidate` reports `invalid`, so a corrupted working copy is not a permanent dead end — the user can still discard it and keep editing, they just cannot open it as-is.

DECISION | Wheeljack | Backup retention matches only this service's own owned-file naming pattern | Every backup filename is `<freeformFilename(title) minus extension>.freeform-backup-<epoch-ms><.freeform>`; retention pruning lists the destination directory, filters to names with that exact title-derived prefix and infix, sorts lexically (which equals chronological order because the timestamp is a fixed-origin integer), and deletes everything past the newest 10. | "No unrelated files deletion" requires an unambiguous, narrow ownership test; matching only this document's own derived prefix (not just the generic `.freeform-backup-` infix) also prevents one show's retention pass from touching another show's backups in the same chosen destination. | Renaming a show's title changes its backup-ownership prefix going forward; older backups under the previous title's prefix are not retroactively claimed or pruned by the new name, and are left for the user to manage manually. This is a known, disclosed limitation, not a defect.

DECISION | Wheeljack | Backup reminder is a pure boolean decision, not a scheduler | `shouldPromptForBackup` takes an explicit `BackupReminderState` (an `unsavedOriginSince` marker plus optional `lastPromptedAt`) and an injectable clock; it never itself sets timers, calls `setInterval`, or writes any state. The 24h interval is evaluated as `now - lastPromptedAt >= 24h` (boundary inclusive). | Browser background-tab timers are unreliable and the spec explicitly forbids assuming a background write; a reminder that is only ever evaluated at actual user-gesture-adjacent moments (app focus, save action, idle check) cannot over-fire while the tab is backgrounded. | M7.3's UI layer owns persisting `unsavedOriginSince`/`lastPromptedAt` across sessions (likely in the ancestry or a small reminder record) and calling this pure function at the moments it chooses; this service makes no promise about exactly when those moments occur.

## Known limitations carried into M7.3

- No UI, bootstrap wiring, or real-browser (Chromium/Firefox/Safari) exercise yet. All of the above is service-layer only, verified with `fake-indexeddb` (a spec-faithful in-memory IndexedDB implementation) plus Vitest fake timers; no code path here has been run against a genuine browser IndexedDB or File System Access implementation.
- `BackupDirectoryHandle`/`SaveFileHandle` destination permission acquisition (the actual user-gesture directory picker call) is M7.3/UI scope, not implemented here; this stage only implements what happens once a destination handle is already available.
- Startup recovery's `listCandidates` takes an explicit list of document IDs; M7.3 owns deciding which document IDs exist to check (e.g. "the one document this single-doc MVP edits") and wiring real browser startup timing.
- `recordRawCheckpoint`'s `migration-original` source is wired and tested as a raw-bytes checkpoint API; no actual 1.x-minor or major migration function exists yet (consistent with the M7.1 decision that no defaultable migration is registered), so it is exercised only with synthetic raw bytes in this stage's tests.
