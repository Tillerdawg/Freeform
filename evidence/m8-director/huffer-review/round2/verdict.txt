FAIL — new reproduced defect (F5), not covered by round-1 F1–F4:

F5 pdf-export.ts345-375 (drawText) + pdf-export.ts593-626 (measuredInkBounds)/634-645 (rotateBounds): rotated multi-font-run text draws at the wrong position relative to its own validated bounds.

drawText() advances `cursor` along the UNROTATED x-axis between font-run flushes, then issues a separate page.drawText(..., {rotate}) call per run using that unrotated cursor as the new rotation pivot. This is correct for single-run text (one font covers the whole string) but wrong whenever a rotated annotation/symbol glyph spans more than one embedded font (e.g. a symbol glyph mixing Latin and emoji codepoints, explicitly schema-legal up to 8000 chars, or any rank/label text requiring a script change under rotation).

Reproduced with symbol glyph 'A😀', rotationDegrees:90, scale:1.5 (evidence/m8-director/huffer-review/round2/all-marks.pdf, 'mixed' symbol annotation) and with rotationDegrees:45, scale:5 at the field's right edge (evidence/m8-director/huffer-review/round2/mixed-edge-symbol.pdf):
- Actual PDF text-matrix origins (pdfjs operator list, round2/results-a.json): run 1 ('A') at (236,377); run 2 ('😀') at (249.419,377) — both using the identical 90° rotation matrix [0,1,-1,0].
- Correct behavior for a single rotated baseline: run 2 must continue along the ROTATED direction from run 1's end, i.e. origin (236 + advance·cos90, 377 + advance·sin90) ≈ (236, 390.42). Instead the actual origin is (249.419, 377) — advanced in raw unrotated x while still being drawn under a 90° rotation matrix. The two runs do not lie on the same rotated baseline; the symbol's second codepoint is drawn disconnected from the first.
- Meanwhile measuredInkBounds()/rotateBounds() — used for the overlap-warning geometry and the off-page preflight assertBoundsOnPage() gate — compute the combined ink box in UNROTATED local space first, then apply one single rigid rotation to the aggregate box. That calculation is internally consistent, but it does not describe where drawText() actually places the second run's glyphs. The preflight check and the overlap warning bounds can therefore both pass (or both approve an export as ok:true) for geometry that does not match what is actually drawn to the page — the opposite failure to F3 (which under-rejected actual off-page content): this is validated geometry silently diverging from drawn geometry.
- Confirmed with the edge case (round2/mixed-edge-symbol.pdf): the second run's unrotated-x-advanced origin before its own local rotation is (800.73, 302) — past the 792-point page width — while the export still returned ok:true. Whether or not visible ink from that specific run lands on-page is incidental; the structural defect is that assertBoundsOnPage/measuredInkBounds no longer describe the same geometry drawText renders whenever a rotated glyph needs more than one font run.

This is in explicit card scope: "Symbols honor actual glyph/anchor/rotation/scale", "geometry is canonical to page... text operators/selectable text and actual embedded font metrics", "Text cannot be silently clipped/truncated/off-page", and the acceptance matrix's "annotation kinds/symbol transform" row. It is not a hypothetical: schema already allows multi-codepoint symbol glyphs (src/document/annotations.ts validateSymbol / assertString 1-8000) and rotation is a first-class symbol property.

Fix direction (not prescriptive of implementation, but the defect class to close): drawText must compute every font-run's origin by advancing along the SAME rotated baseline as prior runs in that call (e.g. precompute total unrotated run offsets first, then apply the single rotation transform to each run's starting point, matching what measuredInkBounds/rotateBounds already do correctly for the aggregate box), so that drawn glyph positions and preflight-validated/reported bounds describe the same geometry for every rotated multi-font-run string. Add a regression test that extracts actual PDF text-matrix origins for a rotated multi-font-run symbol/rank/note and asserts they lie on one consistent rotated line through the anchor, plus that the drawn content does not fall outside the page/validated bounds.
